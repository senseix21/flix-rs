# ADR 002 — fresh wired radio session for development

Date: 2026-10-05. Implemented development workflow; physical UART/radio and actual
QGroundControl qualification remain open. This is not a persistent radio identity.

## Decision

Choose a fresh unpredictable 32-byte signing key generated by the trusted host
tool for every boot/enrollment. The board starts unprovisioned. Send standard
MAVLink SETUP_SIGNING only through the direct trusted wired connection in stopped
exclusive Maintenance. Its timestamp is trusted host MAVLink time at enrollment,
anchored to the board's current monotonic time. Radio never accepts that message
as an ordinary Event. The proxy framing boundary also rejects it.

The [official message layout](https://raw.githubusercontent.com/mavlink/c_library_v2/master/common/mavlink_msg_setup_signing.h)
defines ID 256, CRC extra 71 and the timestamp/target/key fields. The frozen
inventory records this addition. [MAVLink signing](https://mavlink.io/en/guide/message_signing.html)
provides packet authentication and replay handling; it does not encrypt payloads.

Enrollment invalidates command/output authority and replies. Invalid rotation
revokes radio. Zero-key enrollment is explicit wired revocation. The unsigned
wired response carries only success/denial status, never the key. Successful
enrollment does not select a source or arm. UDP endpoint learning resets with
the session epoch; only subsequently accepted radio traffic learns an endpoint.

Outgoing radio replies are signed with link ID 1; the wired reply remains
unsigned. The Python reader checks source 1/1, CRC, signature, timestamp freshness
and monotonically increasing replay state before satisfying requests. Up to four
streams are retained. Signature timestamps outside 48 bits/exhaustion are denied.
Host reply freshness currently uses a 60-second clock-lag allowance.

## Alternatives considered

| Option | Benefit | Cost / unresolved risk |
| --- | --- | --- |
| Fresh trusted wired session | No persistent replay/time transaction; simple stopped enrollment and revoke | Requires direct cable and new key on reboot; relies on trusted tool generating a fresh key |
| Persistent key/time/replay journal | Radio reconnect without wired enrollment | Flash atomicity, clock provenance, captured future packets and rollback must be solved and physically tested |
| Device-generated challenge/session | Can enforce freshness even if host attempts key reuse | Requires audited target entropy, challenge exchange and a new client contract; not established by a host test |

The selected contract relies on the trusted provisioning host generating a new
key. The board does not cryptographically prove host key freshness across reboot.
Reusing an old key through another trusted caller violates this workflow and can
restore old-packet acceptance; a timestamp floor alone does not prevent it.
Persistent unattended operation requires a replacement ADR and evidence.

## Operator workflow

With motor power isolated, the exact board configured and its direct UART adapter
identified:

```sh
mkdir -p .local
PYTHONPATH=tools python3 tools/enroll-radio.py --device /dev/cu.YOUR_UART --session-file .local/flight.session.json
PYTHONPATH=tools python3 tools/enroll-radio.py --device /dev/cu.YOUR_UART --revoke
```

The tool disarms, enters maintenance, waits for its status, enrolls a new random
key, writes an exclusively created private file (0600), then exits maintenance.
Reboot requires new enrollment and a new file; never recycle saved session keys.
Do not route this operation through the ESP-NOW proxy or a network serial server.
UART0 is the current firmware interface; a board's native USB connector is not
automatically that interface. Confirm which port carries UART0 on the actual board.

The physical host/USB path is trusted. Protect the private file and wired captures;
do not record SETUP_SIGNING payloads in general telemetry evidence. Ordinary radio
MAVLink is authenticated but readable. Rust/Python memory is not guaranteed to
erase every compiler/interpreter copy of a secret; no forensic erasure is claimed.

## Evidence and reversal

Host tests exercise stopped enrollment, diagnostic denial, rotation/revoke,
timestamp anchor, wrong key, tampering, duplicates and actual signed Python/Rust
UDP requests. These do not verify the physical cable, RF workload or QGroundControl.
Fixed sender 255/190 is preserved; broader client sender policy needs explicit
interop evidence. Replace this workflow if the supported operator/client cannot
perform fresh wired enrollment or unattended persistent operation is required.
